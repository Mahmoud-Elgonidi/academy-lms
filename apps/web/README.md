# Academy LMS portal

The academies' web portal (Next.js 16, App Router), in two parts:

- **The teacher's portal** (phase A, `/teach`): today, the week, lesson reports, marking homework (recordings play in the page), students and their roadmap, trial lessons, my hours (shift proposals with the academy), time off, earnings, performance, notifications, and the live lesson in the browser (LiveKit, or the teacher's outside link), with a Quran lesson's shared mushaf, whose pages the teacher turns and whose words they mark; a Quran lesson's panel (`/teach/lessons/{id}/quran`: today's portion as three cards, new, near and far review, the way to the mushaf, and the record of what each student recited, mistakes by kind on quick counters or the mushaf's marks, a grade for each part, sent once with an idempotency key), a student's Quran plan with their pace (`/teach/students/{enrollment}/quran`), and the examiner's exams with the result form (`/teach/exams`, in the menu while the academy's plan has the Quran).
- **The family's portal** (phase B, `/family`), for students and guardians, in the look of the person signed in, as in the app and the `/my` panel: a student's own stage (kids, middle school, teens) or the classic look for adults and every guardian. The journey (a student's home, and `/family/journey` for everyone: the academy's own curriculum as islands and stations, the missions to do now, the stars, the week's chest, the egg and the games on each lesson; see `src/components/journey` below), lessons (cancelling after seeing what the policy will do, turning down a substitute, rating a lesson that took place; kids do none of these), the roadmap and the teacher's reports, homework (handed in as words, a voice recording made in the browser, or a picture or PDF; practice in a game plays from the journey), money (what is owed, paid on the academy's own gateway page or by hand with the receipt sent for the academy to confirm; invoices with their tax document; lessons left; the classic look only), notifications, and the hifz map (`/family/hifz`, from the journey's card once the learner has pages on it: every page of the mushaf by part in its strength, and today's review, each page recited into the browser's microphone and checked word by word while the academy has the check on, or recited from memory, uncovered and graded), with the mistakes notebook under it (the words marked in the lessons' shared mushaf; "كلمات بنراجعها" in the kids' look). In a Quran lesson the shared mushaf follows the teacher's page. The Quran's page (`/family/quran`, in the menu after messages while the academy's plan has the Quran, `me.plan_features`): each Quran course's plan (where the learner is, how far along, the next lesson's portion, the last lessons' grades), the thirty parts from the hifz map, today's review, the ways to the hifz map and the mistakes notebook, the exams, and the certificates while the academy shows them (each with its page and its public check); the kids' look in simple words, with stars and no counts. With the plan leaving the Quran out, the Quran's pages (and the hifz map) say so calmly (`components/quran/off.tsx`), never an error page. A guardian with several children picks whose pages they see.

Both portals stay current by themselves (see "Live" below). Staff keep the back office at `/admin`.

It talks only to the API (`/api/v1`, [`packages/openapi/openapi.json`](../../packages/openapi/openapi.json)), as the Flutter app does, and calls the same Actions through it.

## Run it

```bash
# The API with the demo data (apps/api): docker compose up at the root, or
#   composer migrate && php artisan db:seed && php artisan serve
cd apps/web
npm ci
ACADEMY=demo API_INTERNAL_URL=http://127.0.0.1:8000 npm run build
ACADEMY=demo API_INTERNAL_URL=http://127.0.0.1:8000 npm run start   # http://localhost:3000
```

`npm run dev` works the same way. Sign in at http://localhost:3000/ar with `password` as:

- `khaled@demo.test`, a teacher (a report waiting, a recorded homework to mark, a lesson now and then);
- `ziad.guardian@demo.test`, a guardian (an overdue invoice, lessons to cancel or rate), or `yousef.guardian@demo.test`;
- `yousef@demo.test` (kids), `ziad@demo.test` (middle school), `maryam@demo.test` (teen), students in their own looks, each with their journey as home.

Or sign in with a code: it goes to Mailpit (http://localhost:8025) or `apps/api/storage/logs/laravel.log`.

| Setting | What it is |
|---|---|
| `API_INTERNAL_URL` | where the portal's server reaches Laravel: `http://web:8080` in the production stack, `http://127.0.0.1:8000` on a laptop |
| `ACADEMY` | a laptop only: the academy's slug, sent as `X-Academy` (on a server, the host decides, as for the panels) |

Times are shown as the API writes them (`LocalTime.label`, or the wall clock in `local`); calendar days (a week, a month) are written in UTC so a day stays the same day. The portal never converts zones. A clock the portal writes itself (a lesson's start and end from `local`, the hours of the week view) follows how the person reads one, 12 hours (5:00 م, 5:00 PM) or 24 (17:00): their own choice on My account ("شكل الساعة", `PATCH /v1/me`), else the academy's (`Me.time_format`). `formatClock` and `clock` in `lib/time.ts` write it by hand, so the server and the browser write the same; server components take the format from `viewerTimeFormat()`, client components from `useTimeFormat`/`useClock` (`components/time-format.tsx`, provided by both frames). What people type into a native `<input type="time">` shows as the browser and device prefer, and its value stays `HH:MM`.

Times are on the browser's zone (the `lms_tz` cookie the page writes from Intl, sent as `X-Timezone`), unless the person chose one for their account here: the zone chip (`components/zone-chip.tsx`, in both frames but the kids' look: the city and its time ticking on the minute, a dot when the device or the account keeps another clock; opened, their zone, the academy's and the device's, "Use my device's zone", and the cities by region from `GET /v1/timezones`, searched with `lib/zones.ts`) and My account's "توقيتي" (`components/zone-setting.tsx`) save it through `saveZone` (`PATCH /v1/me`), and the browser then sends it instead of the device's (`lms_tz_chosen`, httpOnly; dropped by "Use my device's zone", on signing in or out, and by the chip when the account's zone changed elsewhere). Pages name the zone with `me.timezone_label` ("القاهرة (UTC+2)"). A page with its own bar at a phone's bottom marks it `data-hides-zone-chip`. The person may hide the chip from its card ("أخفِ المؤشّر", `saveZoneChip`: `PATCH /v1/me {zone_chip}`, kept on the account, so the app and the panels follow) and bring it back with the switch on My account (`components/zone-chip-setting.tsx`); the frames leave it out while `me.zone_chip` is false (`zoneChipWanted`).

## Live

A page refreshes itself when something it shows changes elsewhere: a lesson booked, moved or cancelled (also from the phone), homework given, handed in or marked, a message arrived or read, a payment settled. The frame (both shells) holds one socket to Reverb, as the panels do:

- `GET /v1/realtime` (in `lib/live-server.ts`, with the unread count for the badge) says where to listen and the person's own channel (`user.{id}`); the socket goes to the page's own host unless the API names another, so on a server it is `wss://<academy host>/app/<key>`, passed to Reverb by the web part.
- The subscription is signed through `/bff/realtime/auth`, which calls `POST /v1/realtime/auth` with the token from the cookie; the page never holds the token, and the API refuses anyone else's channel.
- `components/live-refresh.tsx`: `LiveRefresh` listens for `lessons.changed`, `homework.changed`, `inbox.changed`, `payments.changed`, `practice.changed` (a round, a creature or a limit; with the other two, what the journey shows), `hifz.changed` (a page reviewed, marked, or recited and then heard) and the rest of `SIGNALS` (no data) and the relay's `resync`, then calls `router.refresh()`, which keeps what is being typed. Each signal is also a window event (`lms:signal`, its name as the detail; `resync` when the relay starts, the socket comes back or the slow timer refreshes), so a client component keeps its own state current (`useSignal`): `mushaf.changed` (the lesson's page turned, a word marked) is only that, the shared mushaf reading its page again, and a page showing what it changes refreshes for it (`RefreshOn`: the mistakes notebook). A hidden tab refreshes when it is looked at again; without a socket, or with the relay quiet for 2.5 minutes, a slow timer (a minute) takes over. `RefreshAt` refreshes at the moments the clock alone changes a page (a lesson's room opening, starting, closing; the week's chest closing on the journey), as the panels' `data-live-next` does.

Locally, run Reverb and the relay next to the API (`php artisan reverb:start --port=8080`, `php artisan live:relay`); without them the pages still work and refresh every minute.
