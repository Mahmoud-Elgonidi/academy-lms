# Academy LMS — notes for Claude

Multi-tenant SaaS LMS for online 1:1 tutoring academies. Architecture (Arabic): `docs/architecture/`. Read the relevant section before changing a module.

## Layout
- `apps/api` — Laravel 13 modular monolith. Modules in `apps/api/modules/<Name>/{src,database,routes,lang,config}`, PSR-4 `Modules\<Name>\` → `src/`. `app/` is composition only.
- `docs/architecture` — the design (features, domain rules, technical architecture, patterns, roadmap).
- `packages/openapi` — the committed OpenAPI document of `/api/v1` (`composer openapi`).
- `apps/mobile` — the Flutter app (guardians, students by stage, teachers). Features in `lib/features/<x>/{data,domain,presentation}`; see its README.
- `apps/web` — the Next.js portal: teachers (`/teach`), students and guardians (`/family`). App Router under `src/app/[locale]`; see its README.
- `tools/course` — the video course (five series, syllabus in `docs/course/README.md`, written by `node syllabus.mjs`): each lesson is a script of steps in `series/*.mjs` played on the real screens with demo data, filmed through Chrome's screencast and put together with ffmpeg (`node record.mjs <series> [n…]`); a narrator from ElevenLabs (`lib/voice.mjs`: `ELEVENLABS_API_KEY`, `ELEVENLABS_VOICE_ID`) speaks each step's `voice:` line, made before filming so each step waits for its line and laid at its caption's moment (cached in `.voice/`). Passwords, 2FA secrets and the key only from env vars; videos stay out of git.

## Commands (run in `apps/api`)
- `composer migrate` — migrations run as `lms_owner`; plain `php artisan migrate` is meant to fail.
- `composer test` — Pest against Postgres `lms_test` with real roles and RLS. Needs Postgres + the roles from `database/setup/roles.sql` (or `docker compose up -d` at the repo root).
- `composer lint` / `vendor/bin/pint` — code style.
- In `apps/mobile`: `flutter analyze`, `flutter test` (includes the contract test against `packages/openapi/openapi.json`), `dart format lib test`; after changing wording `python3 tool/strings.py && flutter gen-l10n`.
- In `apps/web`: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`; `npx playwright test` against a running portal and API with fresh demo data; after the API changes `npm run api:types`.

## Rules
- Tenant tables: `$table->tenant()` + `$table->tenantKey()` + `TenantTable::enableRls()`; models `use BelongsToTenant`; cross-table references via `$table->tenantForeign()`.
- Never use the `pgsql_platform` connection outside `modules/Platform` (arch test).
- Cross-module calls go through `Contracts/` (interfaces, DTOs, events); arch tests enforce the dependency graph in `docs/architecture/04-design-patterns.md`.
- Use cases are `final` Action classes; controllers, Filament pages and jobs call the same Action.
- API errors are RFC 7807 (`Modules\SharedKernel\Http\ProblemDetails`); user-facing strings in `lang/{ar,en}` inside the module.
- UTC everywhere, `CarbonImmutable`; money as minor units + currency (when Billing lands).
- Panels (Filament 5, `app/Providers/Filament`): `academy` (back office, staff), `teach` (teachers), `family` at `/my` (students and guardians). Each module adds screens through its own plugin (`Filament/*Plugin`, `Filament/Teacher/*`, `Filament/Family/*`). Family screens show the learner from `People\Contracts\FamilyView::current()` and check it on every action; never show a family internal notes, teacher pay or KPIs. A student's own area takes the look of their `LearnerStage` (`FamilyView::stage()` of the person signed in: kids, middle, teen; classic for adults and every guardian): give family screens per-stage labels (`nav.{stage}` in lang) and hide what does not fit the stage; the stage shell (font, shapes, phone tab bar) is People's, and stage views use Filament's colour variables like any custom screen. Check permissions with `Gate::allows(Ability::X->value)` (`Modules\SharedKernel\Authorization\Ability`); only Identity maps roles to abilities. Per-user screen choices: declare with `UserPreferences::define()` in the module's provider; they show up on "My settings".
- Motion: every panel loads the shared layer (`shared::motion.styles` in the head, `shared::motion.script` after Livewire). Use its utilities — `.lms-stagger` (children come in one by one), `.lms-lift` (a card you can open), `.lms-bar-fill` (a bar that fills), `data-count` (a number that counts up), `data-celebrate` (confetti when a value grew) — and keep any screen's own animation to transform and opacity, `backwards` fill, inside `@media (prefers-reduced-motion: no-preference)`. Widgets on a first screen are not lazy (`$isLazy = false`), so nothing jumps.
- Frame: every panel also loads `shared::chrome.*` (side menu card and greeting, top bar, sign-in, page changes as View Transitions through Livewire's `wire:transition.navigate`). Don't give elements `view-transition-name` yourself (one element per name, or the browser drops the transition; chrome/script names them); restyle Filament's own parts there, not per screen. A stage shell keeps the last word on its look: chrome rules that a shell also sets stay at or below its specificity (`:where()`).
- Custom screens use Filament's colour variables (`--primary-600`, `--danger-50`, ...) so they follow the academy's branding; never hard-code the brand colour.
- Payments: the academy is the merchant, on its own gateway accounts (`gateway_accounts`, keys only through `SaveGatewayAccount`, never shown or logged). A gateway sits behind `Billing\Payments\PaymentGateway` (HTTP client, no SDK; tests with `Http::fake`). Money counts only when the gateway itself says so: record online payments through `SettleCheckout` alone (one payment per checkout, held by the database); webhooks go into the inbox once and only trigger a settle. Paid by hand, the payer sends a proof (`manual_payment_proofs`: the receipt on the private disk, one pending per invoice) through `SubmitPaymentProof`; it records nothing until staff approve it with `ApprovePaymentProof` (which calls `RecordPayment` with what actually arrived) or turn it down with `RejectPaymentProof` (a reason the payer reads); receipts are served only to their payer and `billing.view`. Gateways: Stripe (the academy's keys, or its own account connected to the platform: `stripe_connect`, made only by `ConnectStripeAccount` from Stripe's OAuth, charged with the platform key and `Stripe-Account`; one platform Connect webhook routed by the checkout's `metadata.academy`), Moyasar, Tap, Paymob (HMAC-checked callback, then `transaction_inquiry`), demo. Every gateway's webhook is refused unless the gateway signed it (Stripe-Signature, Moyasar `secret_token`, Paymob `hmac`, Tap `hashstring`), and the card is typed only on the gateway's page (PCI SAQ A, `Security\PaymentSafetyTest`).
- Invoices: an issued invoice never changes (the model refuses; `credit_notes` by trigger). Seller name, VAT number, `tax_document` and the ZATCA QR are stamped at issue by `Zatca\TaxDocument` (phase 1: simplified tax invoice, TLV base64, riyals only); cancel only through `VoidInvoice`, which issues the credit note for a tax document. Show invoices through `Queries\InvoiceDocument` (back office and the payer's signed `billing.pay.document`).
- Discounts (Billing): what comes off an invoice is worked out by the pure `Domain\Discounts` (the sibling discount from `billing_settings`, ranked by `SiblingRank`; a coupon's terms) and written as its own negative `discount` line by `InvoiceDiscounts`; every invoice goes through `WriteInvoice` (VAT on what is left; one that comes to nothing is settled by `RecordPayment::nothingDue`). Coupons change only through `SaveCoupon` (a used one keeps its code and value), go on a subscription only through `ApplyCoupon` (checked by `CouponCheck`: dates on the academy's calendar, uses, plans, currency, once per payer; `reissue` voids and issues again the waiting block, never an invoice with money, a proof or a checkout on it) and come off through `RemoveCoupon`; a coupon's turns are counted from the invoice lines, never stored. Extra lessons are an `extra` invoice line through `BuyExtraLessons` alone (one waiting per subscription, family discount only), and are booked with `Scheduling\Actions\BookExtraLesson` from the course's own minutes. Other modules ask `BillingApi` (`quote`, `courseBilling`, `applyCoupon`, `removeCoupon`, `sellExtraLessons`).
- Family billing (Billing): an invoice line says which course it is for (`invoice_lines.subscription_id`); `invoices.subscription_id` is only the one course of a single-course invoice, so ask lines (`Invoice::forSubscription`, `subscriptionIds()`, `Queries\InvoiceCourses` for students and subjects), never `invoices.subscription_id`. Renewals go out through `IssueRenewal` alone: the due course's next block plus, on the same invoice (`IssueBlockInvoice::together`), every other course on the payer's account with no block waiting whose paid-for minutes would reach their mark within `billing_settings.family_invoice_days` (0 off) at its plan's pace; each block keeps its own discounts, and paying grants each course its lines. A shared package (`plans.credit_scope = student_pool`) is one credit account for a student's courses on it: a subscription's courses are the enrollments on its credit account (`Subscription::ofEnrollment`, `enrollmentIds()`; one live subscription per account), `EnrollStudent` joins a later course to it through `BillingApi::sharedPackage` (no invoice, no coupon), and `FundSessions` funds the whole balance in date order. A plan's kind never changes once subscribed (`SavePlan`).
- Revenue (Billing, `billing.view`; the accountant lands on it): `Queries\RevenueBoard` reads payments, invoices and lines each time, one currency at a time (never add currencies). Periods are days on the academy's clock (`Support\RevenuePeriod`, day starts through `LocalTimeResolver`; compared with the same days before); collected = payments by `received_at`, its VAT in proportion to the invoice's; a payment is shared between its invoice's courses by `Domain\Revenue\Split` (whole units that add up), so breakdowns (method, kind of sale, subject, plan) always sum to what came in. The forecast uses `IssueRenewal`'s reckoning and `CreditsApi::balances()` (one read for many accounts). It follows `revenue:{academy}` (invoices trigger); `ExportRevenue` writes the period's spreadsheet. The demo's past months come from `Database\Seeders\DemoRevenueSeeder` (real lessons and renewals; runs before the other enrolments so invoice numbers follow the calendar).
- Time off: approved `teacher_time_off` and `academy_holidays` come out of `AvailabilityQuery`, so anything booking through it respects them. A lesson changes teacher only through `SubstituteTeacher` (keeps `original_teacher_id`); lessons lost to leave or a holiday are cancelled through `CancelSession` with the reasons `teacher_leave`, `substitute_refused` (rule 21: makeup) or `holiday` (rule 15: refund, and `CreditsApi::extend` for the days).
- Disputes (Scheduling): the family (not the kids' look) or the lesson's teacher disputes a decided lesson (completed, student or teacher absent) within 48 hours, once per lesson (`session_disputes`, unique), only through `DisputeLesson` (`Domain\Disputes\DisputeRules`: who, until when, reasons that fit the outcome); it sends the lesson to needs review (pay reversed) and the academy hears of it. It is decided only through `ResolveReview` (`DecideDispute`, or the board's "decide"), which needs an answer while a dispute is open, closes it (upheld when the outcome changed, rejected when it stayed) and corrects credit through `CreditsApi::correct` (used ↔ makeup with `restore`/`reclaim` entries; makeup already booked stays the family's, `decision.credit_short`). A side sees only its own dispute (`LessonPresenter`, `FamilyLessonView`); the other side hears the new outcome, never the other's words.
- Clock changes: weekly times stay on the teacher's clock. The DST planner (`PlanDstChanges`, `scheduling:dst`) pairs each lesson with the same one a week before and records a `ShiftNotice` where only the student's hour moved; families hear it through `SendDstNotices` (14 and 2 days before). A weekly time moves for a period only through `ShiftSlotTimes` (the slot ends, a moved copy covers the period, the original comes back; lessons follow by occurrence date), as `DecideDstChange` (keep the student's time) and `ShiftTeacherLessons` (bulk rescheduling) do.
- Calendar (Scheduling, `ViewLiveBoard`): the academy's lessons over a day, a week (Saturday to Friday) or a month on the viewer's clock (`Queries\Calendar\CalendarRange`, day edges through `LocalTimeResolver`) come from `Queries\Calendar\LessonsCalendar` alone (rows, and counts by status, by day in a zone, by teacher and by subject, read in SQL each time; a lesson is the day it starts), narrowed by `CalendarFilter`. A teacher's shifts and time off behind it are `AvailabilityQuery`'s (`working()`); overlapping lessons share a column through `Filament\Calendar\Lanes`. The page follows the board's signal; `ExportLessons` writes the range. Other modules link to it by route name (`filament.academy.pages.calendar`, `?teacher=`/`?student=`).
- Subjects and people by hand: Catalog's subjects have ordered `subject_levels` and their own `subject_categories` (tracks, curricula), changed only through `SaveSubject` (items keep their ids; one a teacher uses stays, held by a restrict FK). Age groups are fixed (`People\Contracts\AgeGroup`, the stages' bounds), not categories. A teacher's profile (`SaveTeacherProfile`: ages, daily cap, per subject a level range and categories; a subject given without details keeps its own) and a student's details (`SaveStudentDetails`: gender, country, grade, `teacher_gender`) are People's; the back-office Teachers, Students and Guardians screens (`People\Filament\Directory`, read through the read-only `Queries\Models\Person`) add people only through `Actions\Directory\*` (accounts through `IdentityApi::createUser`/`updateUser`/`setActive`, never Identity's models), and a child with no way in of their own is a managed minor under a guardian (`AddStudent`, never without one; `UnlinkGuardian` keeps the last). The welcome with the password link is People's (`SendWelcome`, `people.welcome_*`), also for imports. `AvailabilityQuery` drops the days that hold a teacher's daily cap, so every booking respects it; "Find a teacher" filters by level, category and age in SQL.
- CRM (`modules/Crm`) sits on top: nothing depends on it. It follows Scheduling's and Enrollment's events (`TrialLessonBooked`, `SessionFinalized`, `EnrollmentCreated`, ...) and gives a lead's learner an account only through `PrepareLearner` (passwordless; a child under the parent). A trial is an ordinary session (`type=trial`, `funding=free`) booked from Find a teacher in trial mode; its teacher assesses it in the CRM (no lesson report). Scheduling learns trial conversion through its own contract `TrialConversionRates`, which the CRM binds.
- Report questions (Learning): a subject's own questions after the fixed parts of a lesson report live in `report_templates`, one row per version, never changed (grants revoked); save only through `SaveReportTemplate` (`Templates\TemplateDefinition` checks them, at most 12; a question kept with the same type keeps its key, anything new takes a key the subject never used; the same questions make no new version). A lesson report answers the version it was handed in with (`session_reports.template_id`), else its subject's current one (`ReportTemplate::forReport`); answers are checked by `Templates\TemplateAnswers` inside `SubmitSessionReport` and shown through `TemplateAnswers::present`/`ofReport` (written out in the reader's language; families never see a question with `family=false`). The class page's last homework comes from `LearningApi::lastHomework`.
- Lesson materials (Curriculum): `node_resources` on a lesson (a file on the private disk under the academy's folder, or an http(s) link; at most 12; `audience` all or teachers) change only through `Actions\Resources\{Add,Update,Move,Remove}NodeResource` (type from the file's bytes, size by type; a removed or draft-deleted lesson's files leave after commit). Curriculum hands them out without addresses (`CurriculumApi::resources`/`resourceFile`); whoever shows a lesson to someone allowed to see it signs the file through `Learning\Materials\MaterialLinks` (`learning.material`, relative signature on the academy's host, 12 hours), so link visitors, the apps and the portal open it without a token. Teachers and staff get the teachers-only ones (`RoadmapQuery::MATERIALS_TEACHERS`, `planFor(…, forTeacher)`), families never. Staff preview from the builder through `curriculum.resource` (session and `curriculum.manage`).
- Challenges (Learning, the game layer): worked out each time from what happened (`ChallengesQuery`: lessons through `AttendanceApi::lessonsOfStudent`, homework, mastery, engagement, levels), per stage in `ChallengeCatalog`; weeks start Saturday on the student's clock. Only claims are stored (`challenge_claims`, once per challenge and period, through `ClaimChallenge`, which checks again; only the student, never a guardian) and they add to the journey's points. Guardians cheer through `SendCheer` (their own children, five a day). The app and the family home's `ChallengesWidget` show the same board.
- App motion (`apps/mobile/lib/shared/motion`): entrances with `appear`/`staggered`, numbers with `CountUp`, rewards with `Celebration` and `Juice` (our own sounds from `tool/sounds.py`, off in "Me" and in tests); waits go inside the animation's timeline, never a timer, and everything stands still under `MediaQuery.disableAnimations`. Tabs switch through `AnimatedBranches`, pushed screens through `fadeScalePage`.
- Evaluation reads teacher KPIs from the source tables each time (`TeacherKpis`, 90 days; a lesson in `kpi_exclusions` counts for nothing) and keeps only `lesson_ratings`. Ratings go through `RateLesson` (the student or a guardian, a lesson that took place within 14 days). Families never see KPIs; teachers see ratings without names.
- Payroll reads a lesson's pay from Scheduling's events and the policy decision (`teacher_pay_pct`) through `AccrueLessonPay` only; `teacher_earnings` is append-only (a correction is a `reversal` plus a new line) and a closed month (`payroll_periods`) takes no lines, both held by a trigger. Months are on the academy's clock. Teachers' pay is never shown to families.
- Import (`modules/Import`) sits on top: nothing depends on it, and it makes people, profiles and schedules only through each module's contracts (`IdentityApi`, `PeopleApi`, `CatalogApi`, `ScheduleImport`, `BillingApi::adopt`). An importer reads one row and throws a `ValidationException` saying why it cannot; `RowsRunner` keeps each row in its own savepoint, and the dry run (`CheckImport`) rolls the whole file back, so nothing it does may leave the database before commit (messages go out after commit). Sign-in on the panels is `Identity\Filament\Pages\SignIn` (email, phone as typed, or username); an account made for someone gets its first password from their signed welcome link (`identity.welcome`, `SetFirstPassword`). Don't name a Livewire method `upload` (it is `$wire.upload()` in the browser).
- Security (docs/architecture/03, section 11): every answer gets `SharedKernel\Http\SecurityHeaders`; the portal's `next.config.ts` and the image's `infra/deploy/Caddyfile` send the same set, so change all three together. A new open door gets its own tight `throttle:` on top of the named ceilings (`api` per person or address, `links` for signed pages and the class page); `throttle:N,M` counts each route on its own (`SharedKernel\Http\ThrottlePerRoute`, the route's name in the key), so never put two unnamed `throttle:` on one route (they share that route's count). A route that takes another academy's record answers 401/403/404/410/422, never 5xx or 200: `Security\TenantIsolationSweepTest` tries every route, and `TeacherContactPrivacyTest` checks that a teacher never sees a family's email or phone. Uploads: an allowlist of types checked by content (`mimetypes:`), never SVG or HTML, on the private disk under `academies/{academy}/`, and the `Files\CleanFile` rule on every one (ClamAV through `UploadScanner` when `UPLOAD_SCANNER=clamav`; refused while it does not answer unless `UPLOAD_SCAN_REQUIRED=false`). Log lines go through `Logging\RedactPersonalData` (a tap on every channel that writes lines; card numbers masked by Luhn). A sign-in takes as long with or without an account: guards use the `timing-safe` provider, and a password check with no account found calls `Auth\DummyPassword::check`. No other origin calls the API from a browser (`config/cors.php`, `CORS_ALLOWED_ORIGINS`). CI runs `composer audit`, `npm audit` and gitleaks; a look-alike that is not a secret goes into `.gitleaks.toml`.
- Operations (docs/architecture/03, section 12; `infra/deploy/RUNBOOKS.md`): Postgres archives every WAL segment into the `backups` volume (`postgres-start.sh`), and the `backup` part (`backup.sh`) makes a base backup, a dump and a copy of the files each day and keeps `BACKUP_KEEP_DAYS`; `restore.sh` drills (`check`) and restores to a moment into a new volume (`to`, `back`; recovery stays on the base backup's timeline). The `offsite` part (`offsite.sh`, app image with `age`/`rclone`/`psql`) sends each WAL segment, backup and the server's settings to an S3-compatible bucket encrypted to `OFFSITE_AGE_RECIPIENT` (public keys only on the server; never overwrites; `OFFSITE_KEEP_DAYS`, 0 leaves deletion to the bucket); `restore.sh offsite`, `check offsite KEYFILE`, `fetch KEYFILE [TIME]` and `to … offsite` read it back with the private key. Each run is a row in `platform_backups` (written by Postgres' superuser, read on `pgsql_platform`; the off-site copy's are `kind=offsite`, with an hourly `wal` line). A part that runs on its own beats through `SharedKernel\Health\Heartbeats`; reported errors go to `RecentErrors` (redacted); mail that left or failed goes to `MailHealth` (a sender that catches a mail failure calls `MailHealth::failed`); `Platform\Health\SystemHealth` reads them all for the console's System health page (with "Send a test email", also `platform:mail-test`), `GET /health` (statuses only, `HEALTH_TOKEN`) and `platform:health --alert` (mail to the platform team, `AlertRecipients`). A new long-running part gets a heartbeat and a check there; a new file in `infra/deploy` goes into `deploy.sh`'s list and the deploy workflow's copies.
- Audit: a sensitive action (money, policy and its waivers, payroll, imports, passwords, the platform team's steps) calls `AuditTrail::record()` inside its Action; who did it comes from `AuditActor` (Laravel Context: the signed-in user, the platform team and on whose behalf, or the system). `audit_logs` is append-only (trigger); never put a secret in its data. Read it through `AuditEntries` (wording in `shared::audit.actions.{group}.{name}`).
- Platform console (`console` panel, guard `platform`, `platform_admins`, authenticator app required): no `ResolveTenant`; Platform's screens read across academies on `pgsql_platform`, Identity's (new academy, support sign-in) act inside `TenantContext::run`. The platform team reaches an academy's data only by signing in as someone through `StartImpersonation` (reason, 15/30/60 minutes, one-time link on the academy's host); `WatchImpersonation` (in every academy panel) audits on the person's behalf and ends it on time. Nothing may change a password while `AuditActor::current()->onBehalfOf` is set.
- A new email or mobile number is the account's only after a code sent to it comes back (`RequestContactChange`, `ConfirmContactChange`; `otp_challenges.purpose = contact`): not while impersonating, not for a managed minor, never another account's address here. Every change (the person's or staff's `UpdateUserDetails`) raises `ContactChanged`, and Privacy tells the account at once on every channel.
- Sign-in by one-time code: `Identity\Otp\Challenges` holds the rules (hashed code, five tries, one a minute, caps per contact and address) and answers the same with or without an account; the message leaves after the response (`defer`), so tests call `withoutDefer()`. Identity sends through its own `OtpSender` contract, which Communication binds (WhatsApp authentication template, Twilio text, email); never put a code in the message log or a log line outside the log drivers. Discovery across academies reads through Platform's `AccountDirectory` only.
- Two-step sign-in (`Identity\TwoFactor`: Filament's app authentication with recovery codes on `users`, secret encrypted, codes hashed): required of `TwoFactor::REQUIRED_FOR` (owner, admin, accountant) on `/admin` through `RequireTwoFactor`, open to anyone in My settings, and asked on every way in of whoever has it on. A new way to sign in gets its token only through `IssueAccessToken::handle()` (a 403 `two-factor-required` with `two_factor_token`, finished by `CompleteTwoFactorSignIn` at `auth/two-factor`; `two-factor-setup-required` for a required role without it), never `issue()` directly; a panel sign-in ends in Filament's challenge. The platform team, signed in as someone, is not asked and cannot change it (the model refuses); only `ResetTwoFactor` (console, with a reason) clears it. Changes are audited by the model.
- Sign-in with Google and Apple (Identity, `Social\*`): never makes an account. `SignInWithProvider` matches a linked `social_identities` row (provider and `sub`), else a verified email equal to one account's in the academy (linked then, `via=email`, audited), else 404 `social-account-not-found`; then the usual way in (`IssueAccessToken::handle()`, the panel's `SignIn`, so two-step sign-in and guardian consent apply). ID tokens are checked by `IdTokens` alone (no SDK: RS256 from the provider's JWKS, issuer, audience, times, nonce). In a browser everything leaves from the academy's host and comes back to the platform's one callback (`SOCIAL_REDIRECT_BASE/auth/social/{provider}/callback`, no session, Apple posts) through `SocialFlow` (encrypted state with the academy, client, intent, nonce, PKCE), which hands the academy's host a `social_sign_ins` ticket (two minutes, once, only for the browser whose secret's hash is in the state: the panel session, the portal's `lms_social` cookie); panel buttons are `:spa-mode="false"`. Link and unlink only through `LinkSocialIdentity`/`UnlinkSocialIdentity` (not while impersonating, never the last way in); the app sends the phone's ID token (`auth/social`, `accounts/social` for discovery, `me/social`). Providers are on only with the platform's clients in config; nothing else changes when they are off.
- Guardian consent (People): a student under the academy's `consent_age` (`people_settings`; no birth date: managed or linked to a guardian) waits for a guardian's consent before signing in or taking their own seat in a lesson. Who needs it is `ConsentRules` alone; Identity asks its own `SignInGate` contract (People binds `ConsentSignInGate`) in `IssueAccessToken::handle()` (403 `guardian-consent-required`), `canAccessPanel('family')` and the sign-in page, so a new way in goes through those, and Classroom asks `PeopleApi::consentState`. `guardian_consents` is append-only (one live per child, a withdrawal once, by trigger): write it only through `GrantConsent` (the guardian, `family`/`link`), `RecordConsent` (staff, with a note) and `WithdrawConsent` (ends the child's sessions through `IdentityApi::endSessions`). Requests go out after commit (`RequestConsent`, on a new guardian link). If the wording in `lang/*/consent.php` changes in meaning, raise `GuardianConsent::VERSION`.
- SaaS plans (Platform: `saas_plans`, `saas_subscriptions` one current per academy with its own limits and areas, `usage_counters`): modules ask SharedKernel's `AcademyPlan` (`has(Feature)`, `limit(Limit)`, `ensureRoom()`, `requireFeature()`), which Platform binds; an academy on no plan (and no academy) is unlimited. Teachers and active students are held at their one door (`Identity\Actions\CreateUser`, `Enrollment\Actions\CreateEnrollment`, with an advisory lock); video minutes and storage are only watched. A module counts what it owns with `UsageMeters::add()` in its provider (storage adds bytes). An area a plan may leave out belongs to its abilities (`Ability::feature()`, checked in `AbilityMatrix`) and its app routes take `plan.feature:{feature}` before `can:`; keep the area's data flowing when it is out (accrual, CRM tracking), only the screens and new writes stop. Change an academy's plan only through `ChangeAcademyPlan` (reason, audited; old rows kept by trigger). Tests start with no plans (TestCase clears the migration's).
- Support (`modules/Support`) sits on top: nothing depends on it. A family (about the learner on screen; not the kids' look; money only in classic) or a teacher writes through `OpenTicket` (who may write about what is `SupportRules`; staff may write one down for them); every other step is its own Action (`ReplyToTicket`, notes included, `AssignTicket`, `ClassifyTicket`, `ResolveTicket`, `ReopenTicket`, `CloseTicket`, `DecideComplaint`, `SaveSupportTargets`), and `support:follow-up` raises late first answers and closes resolved tickets after a quiet week. `ticket_messages` is append-only (grants revoked); the requester never sees notes, assignments or the complaint's decision (`TicketMessage::isPublic`). A complaint is decided by `complaints.decide` with the academy's own reason (audited); Evaluation reads confirmed complaints through its own `TeacherComplaints` contract, which Support binds. Attachments live on the private disk and are served only to the requester and `tickets.handle`.
- App API: each module mounts `routes/api.php` under `api/v1` with `api, tenant, locale, timezone` (discovery alone has no `tenant`), and calls the same Actions and queries as the screens (move panel-only logic into a `Queries\…` class first). Family endpoints take `learner_id` through `FamilyView::learner()`; writes that move money or lessons get `->middleware('idempotent')`. After changing the API run `composer openapi` and commit `packages/openapi/openapi.json` (CI checks drift and `oasdiff breaking`); describe endpoints with a PHPDoc summary, and fields with comments in the array, not `@var`.
- Mobile app: every API call goes through a feature's repository with `ApiClient` (`_api.get('family/lessons')`, a literal path, so the contract test can read it); calls that move lessons or money pass `idempotent: true`. Show times from the API's `{utc, local, timezone, label}` as written (`LocalTime`, `formats.dart`), never convert zones on the phone. Wording only in `tool/strings.py` (Arabic is Egyptian, as on the web), colours from `context.colors` (the academy's branding, never a hard-coded brand colour), corners and fonts from `context.shape` (the stage). A student's screens fit their stage (no cancelling or rating for kids), and nothing shows a family teacher pay or KPIs. A notification, push or link (`academyapp://app/open/{screen}/{id}`) opens through `targetOf` and `openTarget` (`app/router/targets.dart`: a tab location with `go`, never `push`); Firebase settings come only from `--dart-define` (`FCM_*`), never committed. Testers get builds from `app-release.yml` (after the mobile checks on main, or by hand): split release APKs signed with the key from the secrets (`android/key.properties` written in CI, never committed), a tag `app-v{version}-b{build}` with a GitHub pre-release, and the notes and APKs in the Telegram channel through `tool/release/{notes,telegram}.sh` (the bot token only on curl's stdin). Screens stay live through `Live` (`core/realtime`: one socket on the open account's channel while the app is in front): a screen's `LoadCubit` reloads on `refreshOn: context.read<Live>().on({...})` and at `refreshAt` moments (what the clock alone changes); no polling timers of a screen's own.
- Web portal (`apps/web`, Next.js 16: `proxy.ts` is its middleware; read `node_modules/next/dist/docs` before using an API you are unsure of): the token lives in an httpOnly cookie and only the server calls the API, through `lib/api/server.ts` (`get` in pages, `send` in Server Actions, then `refresh()`); paths are typed from `src/lib/api/schema.ts` (`npm run api:types`, CI checks drift), so a call must name a path the OpenAPI document has. Writes go through Server Actions that call the same endpoints as the app; moving lessons or money passes an `idempotencyKey`. Wording only in `messages/{ar,en}.json` (Egyptian Arabic), colours only from the branding tokens in `globals.css` (`bg-brand`, `text-danger`, ...), times as the API writes them (`LocalTime.label`/`local`; calendar days via `lib/format.ts`, never converting zones). A teacher's pages never show other teachers or families' contact details; families never see pay or KPIs. Family pages take the learner from `lib/family/context` (`family()`: the `lms_learner` cookie, else the first) and the look from the API's `viewer_stage` (`data-stage`: kids, middle, teen, classic), with per-stage labels (`nav.{stage}`) and what a look allows in `lib/family/rules` (money only in the classic look, no cancelling or rating for kids); the API checks each write again. Writes both portals make live in `lib/actions/shared`. Pages stay live through the shells' `LiveRefresh` (one Reverb socket on the person's channel, signed through `/bff/realtime/auth`; a signal calls `router.refresh()`): a new signal a portal page should follow goes into `SIGNALS` in `lib/live.ts`, and what the clock alone changes goes to `RefreshAt` (never a polling timer of your own).
- Deploy (`infra/deploy`, `.github/workflows/deploy.yml`, `apps/api/Dockerfile.prod`): on main it ships once every api and web check on the commit passed (its `checks` job); one image, the command picks the part (`entrypoint.sh`; the portal is the `portal` part, built in the image's Node stage, and the web part passes it `/ar`, `/en`, `/_next`, `/bff`). On a shared server the stack keeps to itself (compose project `academy-lms`, one port on 127.0.0.1, limits, nothing installed or reconfigured); secrets live only in the server's `.env` that `deploy.sh` writes once, never in the repo or a log. A setting the app needs on servers goes into that first-run `.env` (and the README). Demo sign-ins come from `config('app.demo')`, never a literal password; behind a proxy, `TRUSTED_PROXIES`.
- Safeguarding (`modules/Safeguarding`, sits on top: nothing depends on it; docs/architecture/02, section 15): anyone raises a concern through `ReportConcern` alone (a child in the kids' look with a child's categories and no words needed, no "danger now"; a family about the learner on screen; a teacher about a student they taught, never naming a teacher; the office for a phone call), and only `safeguarding.handle` (owner, admin) reads them: every step is its own Action (`AcknowledgeConcern`, `AddConcernNote`, `ClassifyConcern`, `PauseConcernTeacher`, `CloseConcern` with an outcome and an optional reply, `ReopenConcern`), `concern_entries` is append-only, body and reply are encrypted, notifications and the audit carry the number and category, never names or words, and `safeguarding:follow-up` tells the leads again after an hour. The reporter sees status and reply only (`MyConcerns`). Teachers' vetting is People's: `teacher_checks` change only through `AddTeacherCheck` (one waiting per kind, scans on the private disk, served to the teacher and the leads) and `DecideTeacherCheck`; `people:checks` reminds a month before and after expiry. Whether a teacher may teach under-18s is `PeopleApi::clearances()`/`mayTeach()` (the academy's `require_minor_check`, a verified unexpired criminal record check, and the pause from `pauseForMinors`, which the teacher never sees explained); a minor is `ConsentRules::under(…, 18)`. Every booking door in Scheduling calls `Support\MinorsGuard`, and Find a teacher and substitute candidates filter with it, so a new way to book a lesson calls it too. A student's camera at join is `classroom_settings.student_camera` (`JoinTicket.camera`).
- Privacy (`modules/Privacy`, sits on top: nothing depends on it): each module says what it holds about a person through SharedKernel's `Privacy\PersonalDataSource` (`export`, `blockers`, `erase`), registered with `PersonalData::add()` in its provider; a new table with a person's data gets a line there. A copy (`RequestDataExport`, built by `BuildDataExportJob`: a ZIP on the private disk under `academies/{academy}/privacy/`, a week, one a day, downloaded only through the signed relative `privacy.copy`) and erasure (`RequestErasure`, answered within 30 days by `RefuseErasure` with a reason or `ApproveErasure`, refused while `ErasurePreview::blockers()` has anything; `privacy:sweep` erases a day later through `EraseAccount`, which anonymises the account last and goes back to the academy if a blocker came up; `CancelDataRequest` until then) are asked by the person, their guardian in the classic look (`PrivacyRules`) or `privacy.handle`. Correction (docs/architecture/02, section 16): the name and a student's gender, country, grade and `teacher_gender` are put right on the spot by the person or their guardian through `CorrectDetails` (what may be is `EditableDetails`; saved through `IdentityApi::rename` and `PeopleApi::correctStudentDetails`; the audit names fields, never values); anything else is a `correction` request (`RequestCorrection`, one open per person, answered within 30 days by `AnswerCorrection` done with an optional note or refused with a reason). Never put a name or address in an erased request's summary or the audit. The public `/privacy`, `/terms` and `/account-deletion` are `LegalController`'s (the academy's on its host, from `privacy_settings`; the platform's elsewhere, `PLATFORM_LEGAL_NAME`, `PRIVACY_CONTACT_EMAIL`); raise `LegalController::VERSION` when their meaning changes.
- `sessions` is Scheduling's table of lessons; Laravel's web sessions live in `http_sessions`.
- Notifications: declare templates in the module's provider with `NotificationsApi::define(new TemplateDefinition(...))` (wording in the module's `lang/{ar,en}/notifications.php`), send with `NotificationsApi::send(new Message(...))` from a listener on the module's own events; pass instants, `Day`, `Money`, `Localized` and `Translatable` values so each recipient gets their language and time zone. Register where it opens in the panels with `NotificationLinks`.
- Live lessons: Classroom owns rooms and video providers (`VideoProvider`: LiveKit, outside link); attendance is Scheduling's (`attendance_segments`), written only through `AttendanceApi`. Links for people without a web login are signed per person (`NotificationLinks::registerPersonal`).
- Lesson recordings (Classroom): the academy's choice in `classroom_settings` (`recording` off/manual/auto, `recording_media` video/audio/by_age, `recording_days`, `recording_family`, `recording_teacher`, through `SaveRecordingSettings`). Nothing records until everyone the lesson records agreed (`RecordingRules`: the teacher and an adult student for themselves, a child only through a guardian, the office from paper with a note); `recording_consents` is append-only (one live per person, a withdrawal once, by trigger), written only through `GiveRecordingConsent`, `RecordRecordingConsent` and `WithdrawRecordingConsent` (which stops what is running); raise `RecordingConsent::VERSION` if `consent.*` in `lang/*/recordings.php` changes in meaning. Recording goes through the `Recorder` adapter (LiveKit Egress, `ProviderManager::recorder()`) only from `StartRecording`/`StopRecording` (one running per lesson, held by the database; the room's metadata shows everyone the sign), and its state moves only from the recorder's webhooks (`HandleEgressEvent`, never backwards) and `SweepRecordings`. Files leave after `recording_days` unless held (`HoldRecording`) or something open needs them (`Contracts\RecordingHolds`: Classroom binds `AllRecordingHolds`, which asks every class tagged `RecordingHolds::SOURCES`: Support's complaints, Safeguarding's concerns); the row stays. Who watches is `RecordingAccess::watcherAs` alone, and every opening goes through `WatchRecording` (logged in append-only `recording_access_logs`, a signed address per opening, played inline, never a download link).
- Live screens: no `wire:poll` for data that changes in the database. Add a table trigger that raises `pg_notify('lms_live', '{topic}:{id}')` (a learner's family: `lms_notify_family(topic, academy, student)`, People's, raises it for the student and each guardian), map the topic to a data-less `ShouldBroadcastNow` event with `LiveSignals::on()` in the module's provider (private channel authorised there, or the person's own `PersonalChannel`), and refresh the component with `LmsLive.watch()` (shared/live.blade.php). Time-driven changes go to the page as `data-live-next`. `live:relay` does the rest. The apps and the portal listen on `PersonalChannel` through `GET /v1/realtime` and `POST /v1/realtime/auth` (the token signs the subscription).
- Times leave the API only through `LocalTimePresenter::present()` → `{utc, local, timezone, label}` in the viewer's zone (`ViewerTimezone`: `X-Timezone` header → profile → academy → UTC). Wall-clock → UTC only through `LocalTimeResolver` (DST gap → later by the gap; repeated hour → earlier). Timezones are IANA names, never offsets.
