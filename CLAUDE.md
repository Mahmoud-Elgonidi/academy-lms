# Academy LMS — notes for Claude

Multi-tenant SaaS LMS for online 1:1 tutoring academies. Architecture (Arabic): `docs/architecture/`. Read the relevant section before changing a module.

## Layout
- `apps/api` — Laravel 13 modular monolith. Modules in `apps/api/modules/<Name>/{src,database,routes,lang,config}`, PSR-4 `Modules\<Name>\` → `src/`. `app/` is composition only.
- `docs/architecture` — the design (features, domain rules, technical architecture, patterns, roadmap).
- `packages/openapi` — the committed OpenAPI document of `/api/v1` (`composer openapi`).
- `apps/mobile` — the Flutter app (guardians, students by stage, teachers). Features in `lib/features/<x>/{data,domain,presentation}`; see its README.
- `apps/web` — the Next.js portal: teachers (`/teach`), students and guardians (`/family`). App Router under `src/app/[locale]`; see its README.
- `tools/course` — the video course (five series, syllabus in `docs/course/README.md`, written by `node syllabus.mjs`): each lesson is a script of steps in `series/*.mjs` played on the real screens with demo data, filmed through Chrome's screencast and put together with ffmpeg (`node record.mjs <series> [n…]`); a narrator from ElevenLabs (`lib/voice.mjs`: `ELEVENLABS_API_KEY`, `ELEVENLABS_VOICE_ID`) speaks each step's `voice:` line, made before filming so each step waits for its line and laid at its caption's moment (cached in `.voice/`); the model is `eleven_v4` (the voice is Egyptian there), `voice:` lines are written as said in Egyptian with numbers in words and vowels only where a word could be misread, and `node listen.mjs <series> [n…]` lists the words speech to text heard differently; a lesson (or series) may name its own `voice:`, and a `voice:` line may carry a feeling cue (`[warmly]`, `[cheerful]`) the model follows and the subtitles leave out. A series with `app: true` (the guardians') is filmed in the phone app itself: `apps/mobile`'s web build (`flutter build web --no-web-resources-cdn --base-href /app/ --dart-define=API_BASE_URL=http://localhost:8000/api/v1`) served under the API's `/app/`, its parts found by name through Flutter's semantics (`s.tab`, `s.button`, `s.field`). Passwords, 2FA secrets and the key only from env vars; videos stay out of git.

## Commands (run in `apps/api`)
- `composer migrate` — migrations run as `lms_owner`; plain `php artisan migrate` is meant to fail.
- `composer test` — Pest against Postgres `lms_test` with real roles and RLS. Needs Postgres + the roles from `database/setup/roles.sql` (or `docker compose up -d` at the repo root).
- `composer lint` / `vendor/bin/pint` — code style.
- In `apps/mobile`: `flutter analyze`, `flutter test` (includes the contract test against `packages/openapi/openapi.json`), `dart format lib test`; after changing wording `python3 tool/strings.py && flutter gen-l10n`.
- In `apps/web`: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`; `npx playwright test` against a running portal and API with fresh demo data; after the API changes `npm run api:types`.

## Rules
- Tenant tables: `$table->tenant()` + `$table->tenantKey()` + `TenantTable::enableRls()`; models `use BelongsToTenant`; cross-table references via `$table->tenantForeign()`.
- Never use the `pgsql_platform` connection outside `modules/Platform` (arch test).
- Cross-module calls go through `Contracts/` (interfaces, DTOs, events); arch tests enforce the dependency graph in `docs/architecture/04-design-patterns.md`.
- Use cases are `final` Action classes; controllers, Filament pages and jobs call the same Action.
- API errors are RFC 7807 (`Modules\SharedKernel\Http\ProblemDetails`); user-facing strings in `lang/{ar,en}` inside the module.
- Arabic is Modern Standard Arabic everywhere people read it (panels, console, portal, app, messages, the public pages, demo data), simple words in the kids' look; only the course's `voice:` lines are Egyptian. `docs/style/arabic.md` holds the style and the glossary (معلّم, المدفوعات, الرمز, المساعدة, المزيد), and one list of colloquial words is refused by `Arch\ArabicWordingTest`, the portal's `messages.test.ts` and the app's `tool/strings.py`.
- UTC everywhere, `CarbonImmutable`; money as minor units + currency (when Billing lands).
- Panels (Filament 5, `app/Providers/Filament`): `academy` (back office, staff), `teach` (teachers), `family` at `/my` (students and guardians); they share one session, so an account a panel does not take reads who it is with a way out (`App\Http\Middleware\AuthenticateForPanel`, `shared::panels.wrong-account`), never a bare 403. Each module adds screens through its own plugin (`Filament/*Plugin`, `Filament/Teacher/*`, `Filament/Family/*`). Family screens show the learner from `People\Contracts\FamilyView::current()` and check it on every action; never show a family internal notes, teacher pay or KPIs. A student's own area takes the look of their `LearnerStage` (`FamilyView::stage()` of the person signed in: kids, middle, teen; classic for adults and every guardian): give family screens per-stage labels (`nav.{stage}` in lang) and hide what does not fit the stage; the stage shell (font, shapes, phone tab bar) is People's, and stage views use Filament's colour variables like any custom screen. Check permissions with `Gate::allows(Ability::X->value)` (`Modules\SharedKernel\Authorization\Ability`); only Identity maps roles to abilities. Per-user screen choices: declare with `UserPreferences::define()` in the module's provider; they show up on "My settings".
- Motion: every panel loads the shared layer (`shared::motion.styles` in the head, `shared::motion.script` after Livewire). Use its utilities — `.lms-stagger` (children come in one by one), `.lms-lift` (a card you can open), `.lms-bar-fill` (a bar that fills), `data-count` (a number that counts up), `data-celebrate` (confetti when a value grew) — and keep any screen's own animation to transform and opacity, `backwards` fill, inside `@media (prefers-reduced-motion: no-preference)`. Widgets on a first screen are not lazy (`$isLazy = false`), so nothing jumps.
- Frame: every panel also loads `shared::chrome.*` (side menu card and greeting, top bar, sign-in, page changes as View Transitions through Livewire's `wire:transition.navigate`). Don't give elements `view-transition-name` yourself (one element per name, or the browser drops the transition; chrome/script names them); restyle Filament's own parts there, not per screen. A stage shell keeps the last word on its look: chrome rules that a shell also sets stay at or below its specificity (`:where()`).
- Custom screens use Filament's colour variables (`--primary-600`, `--danger-50`, ...) so they follow the academy's branding; never hard-code the brand colour.
- Payments: the academy is the merchant, on its own gateway accounts (`gateway_accounts`, keys only through `SaveGatewayAccount`, never shown or logged). A gateway sits behind `Billing\Payments\PaymentGateway` (HTTP client, no SDK; tests with `Http::fake`). Money counts only when the gateway itself says so: record online payments through `SettleCheckout` alone (one payment per checkout, held by the database); webhooks go into the inbox once and only trigger a settle. Paid by hand, the payer sends a proof (`manual_payment_proofs`: the receipt on the private disk, one pending per invoice) through `SubmitPaymentProof`; it records nothing until staff approve it with `ApprovePaymentProof` (which calls `RecordPayment` with what actually arrived) or turn it down with `RejectPaymentProof` (a reason the payer reads); receipts are served only to their payer and `billing.view`. Where to send the money is the academy's transfer details (plain text, no HTML, up to 1,000 characters: `billing_settings.manual_payment_note` for everyone, a price region's own `price_regions.transfer_details` wins for its payers), saved only through `SaveTransferDetails` (audited without the text) and given to payers only through `Queries\TransferDetails` (an invoice has them only while something is left to pay; none, no proof); show them escaped, line breaks kept, with a copy button, and never in a message body (WhatsApp takes no line breaks: the pay link shows them). Gateways: Stripe (the academy's keys, or its own account connected to the platform: `stripe_connect`, made only by `ConnectStripeAccount` from Stripe's OAuth, charged with the platform key and `Stripe-Account`; one platform Connect webhook routed by the checkout's `metadata.academy`), Moyasar, Tap, Paymob (HMAC-checked callback, then `transaction_inquiry`), demo. Every gateway's webhook is refused unless the gateway signed it (Stripe-Signature, Moyasar `secret_token`, Paymob `hmac`, Tap `hashstring`), and the card is typed only on the gateway's page (PCI SAQ A, `Security\PaymentSafetyTest`).
- Invoices: an issued invoice never changes (the model refuses; `credit_notes` by trigger). Seller name, VAT number, `tax_document` and the ZATCA QR are stamped at issue by `Zatca\TaxDocument` (phase 1: simplified tax invoice, TLV base64, riyals only); cancel only through `VoidInvoice`, which issues the credit note for a tax document and refuses while a receipt waits on the invoice or an online payment on it is under way. Show invoices through `Queries\InvoiceDocument` (back office and the payer's signed `billing.pay.document`).
- Discounts (Billing): what comes off an invoice is worked out by the pure `Domain\Discounts` (the sibling discount from `billing_settings`, ranked by `SiblingRank`; a coupon's terms) and written as its own negative `discount` line by `InvoiceDiscounts`; every invoice goes through `WriteInvoice` (VAT on what is left; one that comes to nothing is settled by `RecordPayment::nothingDue`). Coupons change only through `SaveCoupon` (a used one keeps its code and value), go on a subscription only through `ApplyCoupon` (checked by `CouponCheck`: dates on the academy's calendar, uses, plans, currency, once per payer; `reissue` voids and issues again the waiting block, never an invoice with money, a proof or a checkout on it) and come off through `RemoveCoupon`; a coupon's turns are counted from the invoice lines, never stored. Extra lessons are an `extra` invoice line through `BuyExtraLessons` alone (one waiting per subscription, family discount only), and are booked with `Scheduling\Actions\BookExtraLesson` from the course's own minutes. Other modules ask `BillingApi` (`quote`, `courseBilling`, `applyCoupon`, `removeCoupon`, `sellExtraLessons`).
- Family billing (Billing): an invoice line says which course it is for (`invoice_lines.subscription_id`); `invoices.subscription_id` is only the one course of a single-course invoice, so ask lines (`Invoice::forSubscription`, `subscriptionIds()`, `Queries\InvoiceCourses` for students and subjects), never `invoices.subscription_id`. Renewals go out through `IssueRenewal` alone: the due course's next block plus, on the same invoice (`IssueBlockInvoice::together`), every other course on the payer's account with no block waiting whose paid-for minutes would reach their mark within `billing_settings.family_invoice_days` (0 off) at its plan's pace; each block keeps its own discounts, and paying grants each course its lines. A shared package (`plans.credit_scope = student_pool`) is one credit account for a student's courses on it: a subscription's courses are the enrollments on its credit account (`Subscription::ofEnrollment`, `enrollmentIds()`; one live subscription per account), `EnrollStudent` joins a later course to it through `BillingApi::sharedPackage` (no invoice, no coupon), and `FundSessions` funds the whole balance in date order. A plan's kind and shape (lesson length, lessons a week and per block) never change once subscribed (`SavePlan`; the form locks them): another shape is another plan.
- Revenue (Billing, `billing.view`; the accountant lands on it): `Queries\RevenueBoard` reads payments, invoices and lines each time, one currency at a time (never add currencies). Periods are days on the academy's clock (`Support\RevenuePeriod`, day starts through `LocalTimeResolver`; compared with the same days before); collected = payments by `received_at`, its VAT in proportion to the invoice's; a payment is shared between its invoice's courses by `Domain\Revenue\Split` (whole units that add up), so breakdowns (method, kind of sale, subject, plan) always sum to what came in. The forecast uses `IssueRenewal`'s reckoning and `CreditsApi::balances()` (one read for many accounts). It follows `revenue:{academy}` (invoices trigger); `ExportRevenue` writes the period's spreadsheet. The demo's past months come from `Database\Seeders\DemoRevenueSeeder` (real lessons and renewals; runs before the other enrolments so invoice numbers follow the calendar).
- Time off: approved `teacher_time_off` and `academy_holidays` come out of `AvailabilityQuery`, so anything booking through it respects them. A lesson changes teacher only through `SubstituteTeacher` (keeps `original_teacher_id`); lessons lost to leave or a holiday are cancelled through `CancelSession` with the reasons `teacher_leave`, `substitute_refused` (rule 21: makeup) or `holiday` (rule 15: refund, and `CreditsApi::extend` for the days).
- Pausing and ending a course (docs/architecture/02, section 3, "إيقاف الكورس وإنهاؤه"): days on the academy's calendar (`Scheduling\Support\CourseDays`; a lesson is the day it starts there), by staff only and only through Scheduling's `Actions\Courses\{PauseEnrollment,ResumeEnrollment,EndEnrollment}` (each with a `preview`, a reason, audited `enrollment.paused|resumed|ended`), which write the course through `EnrollmentApi::pause|resume|end` (Enrollment's `PauseCourse`/`ResumeCourse`/`EndCourse` hold its rules: pause only a running course, from today, at most 120 days, made only longer; an ended course never comes back). Their lessons are cancelled through `CancelSession` with `enrollment_paused`/`enrollment_ended` (rule 22: minutes back to the balance, no pay); a pause extends the credit (`CreditsApi::extend`, not while another course draws on a shared balance) and keeps the weekly times; an end trims them at its day and, once the day has come, closes the waiting block and extra-lessons invoices through `BillingApi::closeEndedCourse` (voided only with nothing paid, no proof, no open checkout; a family invoice comes out again without it; a shared package's stays). A block paid during a pause lasts the pause's remaining days longer (`RecordPayment::fulfil`); the office's early resume needs room in the academy's plan (`ResumeCourse`), the planned return does not. A pause or end set ahead takes effect through `scheduling:courses` (hourly, `FollowCourseDays`, which also resumes on the day after the pause). Nothing renews unless `Subscription::taught` (active, no `ends_on`); lessons are made only for `EnrollmentStatus::makesLessons()` and never on a paused day or after the end; every way to book or move a course's lesson calls `CourseDays::assertOpen`. The family reads `status`, `paused_until` and `ends_on` (`LocalTimePresenter::academyDay`), never the reason; Enrollment's `EnrollmentPaused`/`Resumed`/`Ended` drive one message each (`scheduling.course_*`).
- Disputes (Scheduling): the family (not the kids' look) or the lesson's teacher disputes a decided lesson (completed, student or teacher absent) within 48 hours, once per lesson (`session_disputes`, unique), only through `DisputeLesson` (`Domain\Disputes\DisputeRules`: who, until when, reasons that fit the outcome); it sends the lesson to needs review (pay reversed) and the academy hears of it. It is decided only through `ResolveReview` (`DecideDispute`, or the board's "decide"), which needs an answer while a dispute is open, closes it (upheld when the outcome changed, rejected when it stayed) and corrects credit through `CreditsApi::correct` (used ↔ makeup with `restore`/`reclaim` entries; makeup already booked stays the family's, `decision.credit_short`). A side sees only its own dispute (`LessonPresenter`, `FamilyLessonView`); the other side hears the new outcome, never the other's words.
- Clock changes: weekly times stay on the teacher's clock. The DST planner (`PlanDstChanges`, `scheduling:dst`) pairs each lesson with the same one a week before and records a `ShiftNotice` where only the student's hour moved; families hear it through `SendDstNotices` (14 and 2 days before). A weekly time moves for a period only through `ShiftSlotTimes` (the slot ends, a moved copy covers the period, the original comes back; lessons follow by occurrence date), as `DecideDstChange` (keep the student's time) and `ShiftTeacherLessons` (bulk rescheduling) do.
- Calendar (Scheduling, `ViewLiveBoard`): the academy's lessons over a day, a week (Saturday to Friday) or a month on the viewer's clock (`Queries\Calendar\CalendarRange`, day edges through `LocalTimeResolver`) come from `Queries\Calendar\LessonsCalendar` alone (rows, and counts by status, by day in a zone, by teacher and by subject, read in SQL each time; a lesson is the day it starts), narrowed by `CalendarFilter`. A teacher's shifts and time off behind it are `AvailabilityQuery`'s (`working()`); overlapping lessons share a column through `Filament\Calendar\Lanes`. The page follows the board's signal; `ExportLessons` writes the range. Other modules link to it by route name (`filament.academy.pages.calendar`, `?teacher=`/`?student=`).
- Subjects and people by hand: Catalog's subjects have ordered `subject_levels` and their own `subject_categories` (tracks, curricula), changed only through `SaveSubject` (items keep their ids; one a teacher uses stays, held by a restrict FK). Age groups are fixed (`People\Contracts\AgeGroup`, the stages' bounds), not categories. A teacher's profile (`SaveTeacherProfile`: ages, daily cap, per subject a level range and categories; a subject given without details keeps its own) and a student's details (`SaveStudentDetails`: gender, country, grade, `teacher_gender`) are People's; the back-office Teachers, Students and Guardians screens (`People\Filament\Directory`, read through the read-only `Queries\Models\Person`) add people only through `Actions\Directory\*` (accounts through `IdentityApi::createUser`/`updateUser`/`setActive`, never Identity's models), and a child with no way in of their own is a managed minor under a guardian (`AddStudent`, never without one; `UnlinkGuardian` keeps the last). The welcome with the password link is People's (`SendWelcome`, `people.welcome_*`), also for imports. `AvailabilityQuery` drops the days that hold a teacher's daily cap, so every booking respects it; "Find a teacher" filters by level, category and age in SQL.
- CRM (`modules/Crm`) sits on top: nothing depends on it. It follows Scheduling's and Enrollment's events (`TrialLessonBooked`, `SessionFinalized`, `EnrollmentCreated`, ...) and gives a lead's learner an account only through `PrepareLearner` (passwordless; a child under the parent). A trial is an ordinary session (`type=trial`, `funding=free`) booked from Find a teacher in trial mode; its teacher assesses it in the CRM (no lesson report). Scheduling learns trial conversion through its own contract `TrialConversionRates`, which the CRM binds.
- The academy's page (`modules/Site`, sits on top: only Crm uses its Contracts; docs/architecture/02, section 24): off until owner or admin turn it on (`site_settings`, words ar+en normalized by the pure `Domain\SiteContent` with defaults that name no academy, saved only through `SaveSiteSettings`, `site.manage`, audited with section names only). `GET v1/site` (404 while off; never an email, a number, pay, KPIs, vetting or a pause) gives the words, Catalog's subjects with levels and Curriculum's programs, the teachers' cards from `PeopleApi::publicTeachers` alone, `BillingApi::planOptions` with a price per region and the regions with their `countries` (ISO, one region each, `SavePriceRegions`), and a `FormToken`. Requests (`site_requests`: a free trial or "teach with us") go only through `SubmitJoinRequest` (`throttle:5,60`; a filled hidden field or a token under 3 seconds is answered the same and kept nowhere; one a week per number and kind); `JoinRequested` (after commit) tells whoever answers that kind (`site.request_new`, the kind only; `Support\RequestAccess`: trials to `leads.manage`, or `site.manage` when the plan has no CRM; teachers to `teachers.manage`) and the CRM makes a trial a lead (`FollowSiteRequests` → `CreateLead`, source website, or an activity on the open lead with that number; never an error to the visitor), answered through `HandleJoinRequest`; `site:sweep` drops them after a year. A teacher's card (`teacher_public_cards`) is theirs alone to write and switch on (`SaveTeacherCard`: /teach "My card", `GET`/`POST v1/teacher/card`; a PNG, JPEG or WebP by its bytes on the public disk under `site/{academy}/teachers/`), and the academy only hides it (`HideTeacherCard`), never says why to the page.
- The platform's page (Platform, `pgsql_platform`; docs/architecture/02, section 23): its words (`platform_site`, `Site\SiteContent`) are saved only by an owner through `SaveSiteContent` (console › Site), the plans it shows are `saas_plans.shown_on_site`/`highlight`/`tagline_*` (`SavePlan`), and an academy asks to join only through `SubmitSignupRequest` (`platform_signup_requests`, the same FormToken and hidden field, `throttle:5,60`, mail to the active owners after commit), answered in console › Requests (`HandleSignupRequest`; "make the academy" fills `NewAcademy` from it and marks it made); `platform:site-sweep` drops the unmade after 12 months. `GET v1/site/platform` answers 404 on an academy's address.
- Report questions (Learning): a subject's own questions after the fixed parts of a lesson report live in `report_templates`, one row per version, never changed (grants revoked); save only through `SaveReportTemplate` (`Templates\TemplateDefinition` checks them, at most 12; a question kept with the same type keeps its key, anything new takes a key the subject never used; the same questions make no new version). A lesson report answers the version it was handed in with (`session_reports.template_id`), else its subject's current one (`ReportTemplate::forReport`); answers are checked by `Templates\TemplateAnswers` inside `SubmitSessionReport` and shown through `TemplateAnswers::present`/`ofReport` (written out in the reader's language; families never see a question with `family=false`). The class page's last homework comes from `LearningApi::lastHomework`.
- Lesson materials (Curriculum): `node_resources` on a lesson (a file on the private disk under the academy's folder, or an http(s) link; at most 12; `audience` all or teachers) change only through `Actions\Resources\{Add,Update,Move,Remove}NodeResource` (type from the file's bytes alone, never the browser's word; size by type; a removed or draft-deleted lesson's files leave after commit). Curriculum hands them out without addresses (`CurriculumApi::resources`/`resourceFile`); whoever shows a lesson to someone allowed to see it signs the file through `Learning\Materials\MaterialLinks` (`learning.material`, relative signature on the academy's host, 12 hours), so link visitors, the apps and the portal open it without a token. Teachers and staff get the teachers-only ones (`RoadmapQuery::MATERIALS_TEACHERS`, `planFor(…, forTeacher)`), families never. Staff preview from the builder through `curriculum.resource` (session and `curriculum.manage`).
- The journey (Learning, docs/architecture/02 section 18): one journey per course, built from the academy's own curriculum only (`Queries\Journey\JourneyMap`, `GET learning/journey/map`): levels are islands (drawn as the world's islands in turn), lessons are stations, missions are only the next lesson, the teacher's homework and reviews due, and stars are the one reckoning (`Domain\Journey\{LessonStars, Stars}`, `StarsQuery`, counted each time: a lesson by lateness from `first_join_at` and staying to the end, rounds, homework, mastered lessons, chests). The week's chest opens only through `OpenWeeklyChest` (the student, once; `challenge_claims` `chest`). Nothing in it knows a subject or a language. The games are a layer through Learning's own `JourneyGames` (Games binds `GamesForJourney`; default `NoJourneyGames`), so the journey stands without them; `learning_settings.journey_style` (playful, calm, plain) through `SaveJourneyStyle`. Guardians cheer through `SendCheer` (their own children, five a day). The old challenges (`ChallengesQuery`, `ChallengeCatalog`, `ClaimChallenge`, `learning/challenges`, `learning/journey`) stay only for earlier app versions: new screens use the journey.
- App motion (`apps/mobile/lib/shared/motion`): entrances with `appear`/`staggered`, numbers with `CountUp`, rewards with `Celebration` and `Juice` (our own sounds from `tool/sounds.py`, off in "Me" and in tests); waits go inside the animation's timeline, never a timer, and everything stands still under `MediaQuery.disableAnimations`. Tabs switch through `AnimatedBranches`, pushed screens through `fadeScalePage`.
- Evaluation reads teacher KPIs from the source tables each time (`TeacherKpis`, 90 days; a lesson in `kpi_exclusions` counts for nothing) and keeps only `lesson_ratings`. Ratings go through `RateLesson` (the student or a guardian, a lesson that took place within 14 days). Families never see KPIs; teachers see ratings without names.
- Payroll reads a lesson's pay from Scheduling's events and the policy decision (`teacher_pay_pct`) through `AccrueLessonPay` only; `teacher_earnings` is append-only (a correction is a `reversal` plus a new line) and a closed month (`payroll_periods`) takes no lines, both held by a trigger. Months are on the academy's clock. Teachers' pay is never shown to families.
- Import (`modules/Import`) sits on top: nothing depends on it, and it makes people, profiles and schedules only through each module's contracts (`IdentityApi`, `PeopleApi`, `CatalogApi`, `ScheduleImport`, `BillingApi::adopt`). An importer reads one row and throws a `ValidationException` saying why it cannot; `RowsRunner` keeps each row in its own savepoint, and the dry run (`CheckImport`) rolls the whole file back, so nothing it does may leave the database before commit (messages go out after commit). Sign-in on the panels is `Identity\Filament\Pages\SignIn` (email, phone as typed, or username); an account made for someone gets its first password from their signed welcome link (`identity.welcome`, `SetFirstPassword`). Don't name a Livewire method `upload` (it is `$wire.upload()` in the browser).
- Security (docs/architecture/03, section 11): every answer gets `SharedKernel\Http\SecurityHeaders`; the portal's `next.config.ts` and the image's `infra/deploy/Caddyfile` send the same set, so change all three together. Pages run only their own files and scripts with the request's nonce (`ContentSecurityPolicy`: `script-src 'self' 'nonce-…' 'unsafe-eval'` for Alpine and Livewire; the portal's `proxy.ts` and `lib/csp.ts` with `'strict-dynamic'`): a Blade precompiler gives every `<script>` a template writes the nonce, so write scripts as `<script>` tags in templates, never `on…=` handlers or `javascript:` links (`HttpHardeningTest` looks), and never build one from data; a portal script of its own takes `x-nonce`. A new open door gets its own tight `throttle:` on top of the named ceilings (`api` per person or address, `links` for signed pages and the class page); `throttle:N,M` counts each route on its own (`SharedKernel\Http\ThrottlePerRoute`, the route's name in the key), so never put two unnamed `throttle:` on one route (they share that route's count). A route that takes another academy's record answers 401/403/404/410/422, never 5xx or 200: `Security\TenantIsolationSweepTest` tries every route, and `TeacherContactPrivacyTest` checks that a teacher never sees a family's email or phone. Uploads: an allowlist of types checked by content (`mimetypes:`), never SVG or HTML, on the private disk under `academies/{academy}/`, and the `Files\CleanFile` rule on every one (ClamAV through `UploadScanner` when `UPLOAD_SCANNER=clamav`; refused while it does not answer unless `UPLOAD_SCAN_REQUIRED=false`). Log lines go through `Logging\RedactPersonalData` (a tap on every channel that writes lines; card numbers masked by Luhn). A sign-in takes as long with or without an account: guards use the `timing-safe` provider, and a password check with no account found (or an account with no password yet) calls `Auth\DummyPassword::check`. No other origin calls the API from a browser (`config/cors.php`, `CORS_ALLOWED_ORIGINS`). CI runs `composer audit`, `npm audit` and gitleaks; a look-alike that is not a secret goes into `.gitleaks.toml`.
- Operations (docs/architecture/03, section 12; `infra/deploy/RUNBOOKS.md`): Postgres archives every WAL segment into the `backups` volume (`postgres-start.sh`), and the `backup` part (`backup.sh`) makes a base backup, a dump and a copy of the files each day and keeps `BACKUP_KEEP_DAYS`; `restore.sh` drills (`check`) and restores to a moment into a new volume (`to`, `back`; recovery stays on the base backup's timeline). The `offsite` part (`offsite.sh`, app image with `age`/`rclone`/`psql`) sends each WAL segment, backup and the server's settings to an S3-compatible bucket encrypted to `OFFSITE_AGE_RECIPIENT` (public keys only on the server; never overwrites; `OFFSITE_KEEP_DAYS`, 0 leaves deletion to the bucket); `restore.sh offsite`, `check offsite KEYFILE`, `fetch KEYFILE [TIME]` and `to … offsite` read it back with the private key. Each run is a row in `platform_backups` (written by Postgres' superuser, read on `pgsql_platform`; the off-site copy's are `kind=offsite`, with an hourly `wal` line).
